플랫폼형 블로그를 쓰다 보면 하루에 올릴 수 있는 글 수가 정해져 있다.
밀린 글이 있어도 내일로 미뤄야 한다.

깃허브 블로그로 옮기면 가장 먼저 궁금해지는 게 이거다.
**여기는 몇 개까지 올릴 수 있나?**

결론부터. **글 개수 제한은 없다.** 하루에 50편을 올려도 막히지 않는다.

## 공식 한도 전부

GitHub Pages가 명시하는 사용 한도는 이게 전부다.

| 항목 | 한도 |
|---|---|
| **글·페이지 개수** | **제한 없음** |
| 계정당 user/organization 사이트 | 1개 |
| 소스 저장소 크기 | 1GB 권장 |
| 발행된 사이트 크기 | 1GB 이하 |
| 배포 시간 | 10분 초과 시 타임아웃 |
| 대역폭 | 월 100GB (소프트) |
| **빌드 횟수** | **시간당 10회 (소프트)** |

글 개수가 아니라 **빌드 횟수**가 제한된다는 게 핵심이다.
글은 저장소의 마크다운 파일일 뿐이고, 개수를 세는 주체가 아예 없다.

> 이 한도들은 GitHub Pages를 **상업 호스팅으로 쓰지 말라**는 약관과 한 묶음이다.
> 온라인 쇼핑몰이나 SaaS를 올리는 용도는 허용되지 않는다. 블로그는 해당 없다.
{: .prompt-info }

## 시간당 10회 — 어떻게 걸리나

푸시 한 번이 빌드 한 번이다. 그래서 이런 식으로 쓰면 걸린다.

```console
$ git add _posts/글1.md && git commit -m "글1" && git push   # 빌드 1
$ git add _posts/글2.md && git commit -m "글2" && git push   # 빌드 2
...
$ git add _posts/글11.md && git commit -m "글11" && git push  # 한 시간 안에 11번째
```

글 하나 쓸 때마다 커밋·푸시하는 습관이면 한 시간에 열 번을 넘기기 쉽다.
오타 고치고 다시 푸시하는 것도 한 번으로 센다.

### 피하는 법 ① — 묶어서 푸시

```console
$ git add _posts/
$ git commit -m "글 5편 추가"
$ git push    # 빌드 1회
```

글 10편을 한 커밋에 담아도 **빌드는 한 번**이다.
이것만으로 대부분 해결된다.

### 피하는 법 ② — Actions 워크플로로 배포

공식 문서에 이렇게 적혀 있다.

> GitHub Pages sites have a soft limit of 10 builds per hour.
> **This limit does not apply if you build and publish your site with a custom GitHub Actions workflow.**

즉 **직접 만든 Actions 워크플로로 빌드·배포하면 이 제한이 아예 없다.**

내 저장소가 어느 쪽인지는 파일 하나로 확인된다.

```console
$ ls .github/workflows/
pages-deploy.yml
```

이 파일이 있고 레포 `Settings → Pages → Source`가 **GitHub Actions**로 되어 있으면
Actions 방식이다. Chirpy를 비롯한 요즘 테마 대부분이 이 구조로 온다.

`Deploy from a branch`로 되어 있으면 깃허브가 알아서 Jekyll을 돌리는 방식이고,
이쪽이 시간당 10회 제한을 받는다.

> Actions 방식으로 바꾸면 **Jekyll 플러그인 제한도 같이 풀린다.**
> 깃허브 기본 빌드는 허용된 플러그인만 쓸 수 있지만,
> Actions는 내 `Gemfile`을 그대로 설치하므로 아무 플러그인이나 쓸 수 있다.
{: .prompt-tip }

Actions 사용량이 따로 있긴 한데, **공개 저장소는 무료 무제한**이다.
블로그를 공개로 두는 이상 신경 쓸 일이 없다.

## 그래서 실제로 뭘 조심하나

| 걱정 | 실제 |
|---|---|
| 하루에 몇 편까지? | 제한 없음 |
| 빌드 10회가 부담되나? | Actions 방식이면 해당 없음, 아니면 묶어서 푸시 |
| 1GB를 넘기나? | 글은 텍스트다. 이미지를 레포에 쌓지만 않으면 멀다 |
| 100GB 트래픽? | 개인 블로그로는 닿기 어렵다 |

현실적으로 신경 쓸 건 **이미지**뿐이다.
스크린샷을 원본 그대로 계속 커밋하면 1GB는 생각보다 빨리 찬다.
깃 저장소는 한번 들어간 파일을 히스토리에 계속 들고 있어서, 지워도 용량이 안 줄어든다.

## 발행 시점을 나누고 싶다면

한도 때문이 아니라 **글이 한 날짜에 몰리는 게 싫어서** 나누고 싶을 때가 있다.
이건 커밋과 무관하게 front matter로 해결된다.

```yaml
---
title: "나중에 보일 글"
date: 2026-11-01 09:00:00 +0900
---
```

Jekyll은 기본적으로 **미래 날짜 글을 빌드에서 뺀다.**
10편을 한 번에 커밋해두고 날짜만 분산시키면, 그날이 와서 빌드가 돌 때 하나씩 나온다.

다만 "그날이 와서 빌드가 돌 때"가 조건이다. 푸시가 없으면 빌드도 없다.
자동으로 나오게 하려면 워크플로에 스케줄을 넣어야 한다.

```yaml
on:
  push:
    branches: [main]
  schedule:
    - cron: '0 0 * * *'   # 매일 09:00 KST
```

여기까지 하면 플랫폼형 블로그의 예약발행과 같은 효과가 난다.
차이가 있다면, 이쪽은 **내가 조건을 정한다**는 점이다.
