**결론:** CPU는 메모리를 바이트 하나씩이 아니라 **캐시 라인**(이 샌드박스는 64바이트) 단위로 가져온다. 배열을 메모리에 놓인 순서대로 읽으면 한 번 가져온 64바이트를 16번(int 기준) 쓰고, 건너뛰며 읽으면 한 번 가져온 64바이트에서 4바이트만 쓰고 버린다. 계산은 똑같은데 시간은 12배 차이가 났다.

> 측정 환경: Intel Xeon 2.1GHz 4코어 가상 머신, Linux 6.18, gcc 13.3.0 `-O1`, 메모리 16GB. 다른 환경에서는 배율이 달라진다. 일반화하지 않는다.
{: .prompt-info }

## 같은 합계, 읽는 순서만 다르다

C의 2차원 배열은 한 행이 끝나면 다음 행이 이어 붙는 식(행 우선)으로 메모리에 놓인다. `a[i*N+j]`에서 `j`가 1 늘면 4바이트 옆, `i`가 1 늘면 `N*4`바이트(32KiB) 옆이다.

```c
#define N 8192
int *a = malloc((size_t)N*N*sizeof(int));   /* 256MiB */
/* 행 순서 */ for(i) for(j) s += a[(size_t)i*N + j];
/* 열 순서 */ for(j) for(i) s += a[(size_t)i*N + j];
```

세 번 반복한 실제 출력:

```
row-order 0.060s  col-order 0.758s  ratio 12.7x  sums 234881024 234881024
row-order 0.059s  col-order 0.741s  ratio 12.6x  sums 234881024 234881024
row-order 0.059s  col-order 0.745s  ratio 12.6x  sums 234881024 234881024
```

두 합계가 같으므로 한 일은 같다. 달라진 것은 메모리를 건드리는 순서뿐이다.

## 캐시 라인 크기는 시스템이 알려 준다

```
$ getconf LEVEL1_DCACHE_LINESIZE
64
$ cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
64
```

리눅스 커널 문서는 `coherency_line_size`를 "메모리에서 캐시로 옮겨지는 최소 데이터 양(바이트)"으로 설명한다([sysfs-devices-system-cpu](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-devices-system-cpu)). 이 문서를 읽은 것이고, 위 `64`는 직접 확인한 값이다.

## 보폭을 늘려 가며 재 보기

1GiB(int 2^28개) 배열에서 `k`칸씩 건너뛰며 읽고 3회 중 최소 시간을 쟀다.

```
stride  1 ints (  4 B): touches 268435456  0.261s
stride  2 ints (  8 B): touches 134217728  0.213s
stride  4 ints ( 16 B): touches  67108864  0.166s
stride  8 ints ( 32 B): touches  33554432  0.143s
stride 16 ints ( 64 B): touches  16777216  0.114s
stride 32 ints (128 B): touches   8388608  0.077s
stride 64 ints (256 B): touches   4194304  0.049s
```

- 보폭 1에서 16으로 가면 읽는 원소는 **16배 줄지만** 시간은 2.3배밖에 안 준다. 원소를 줄여도 가져와야 할 캐시 라인 수(1GiB / 64B ≈ 1677만)는 그대로이기 때문이다.
- 보폭 16(=64바이트)부터는 원소마다 새 라인이라, 보폭이 두 배가 될 때마다 가져오는 라인 수가 반이 되고 시간도 줄어든다.

앞의 12배는 이 현상이 극단으로 간 모습이다. 열 순서의 보폭은 8192칸(32KiB)이라 매번 새 라인을 가져온다.

> 이 측정이 보여 주지 못하는 것: 하드웨어 프리페처가 얼마나 도왔는지, 라인 하나당 정확히 몇 ns인지는 따로 재지 않았다. 위 수치로 말할 수 있는 것은 "라인 수에 시간이 묶여 있다"까지다.
{: .prompt-warning }

## 판별법

"같은 계산인데 입력 크기에 비해 느리다"가 **알고리즘** 때문인지 **메모리 접근 순서** 때문인지는 이렇게 가린다.

1. 읽는 순서만 바꿔서(행↔열) 시간을 잰다. 결과가 같은데 시간이 크게 달라지면 캐시 쪽이다.
2. 보폭을 1, 2, 4, …로 늘려 보고, 64바이트 근처에서 꺾이는지 본다. `getconf LEVEL1_DCACHE_LINESIZE` 값과 맞으면 캐시 라인이 원인이다.
3. 배열이 작으면(캐시에 다 들어가면) 차이가 줄어든다. 이 글은 256MiB·1GiB로 일부러 캐시보다 크게 잡았다. 이 머신의 L3는 `lscpu`상 260MiB로 표시되는데, 가상 머신이 보고한 값이라 실제 점유 용량으로 믿지 않았다.
