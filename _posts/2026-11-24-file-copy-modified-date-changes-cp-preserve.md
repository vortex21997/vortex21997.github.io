**복사본은 내용만 같은 "새 파일"이라서 수정한 날짜가 복사한 순간으로 찍힌다.** 원래 파일의 시각을 같이 가져오고 싶으면 따로 요청해야 한다. 리눅스에서는 `cp -p`가 그 요청이다. 아래는 직접 돌려서 확인한 결과다.

> 확인 환경: Linux 6.18.44, ext4, GNU coreutils 9.4 (`cp`, `stat`). 윈도우와 맥의 복사 동작은 이 글에서 확인하지 않았다. 파일 관리자마다 다를 수 있다.
{: .prompt-info }

## 파일에는 시각이 여러 개 붙어 있다

파일 목록에서 보이는 "수정한 날짜"는 파일에 붙은 여러 시각 중 하나다. 운영체제는 파일 내용과 별도로 **메타데이터**(파일에 대한 부가 정보: 크기, 소유자, 시각 등)를 갖고 있고, 리눅스 man 페이지 [inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html)는 시각을 이렇게 나눈다.

| 이름 | 뜻 (man 페이지 설명을 줄임) | 바뀌는 때 |
|---|---|---|
| mtime | 마지막 **수정** 시각 | 내용을 쓸 때 (`write` 등) |
| ctime | 마지막 **상태 변경** 시각 | 내용을 쓰거나 소유자·권한 같은 파일 정보를 바꿀 때 |
| atime | 마지막 **접근** 시각 | 읽을 때 |

파일 관리자의 "수정한 날짜"는 보통 mtime이다. 아래에서는 `stat`으로 mtime, ctime, 그리고 파일이 만들어진 시각(birth)을 같이 본다.

## 실험: 같은 파일을 세 가지 방법으로 옮겨 보기

2026-01-05 10:00으로 시각을 맞춘 `a.txt`를 만들고, 2초 뒤에 세 가지를 했다.

```bash
echo hello > a.txt
touch -d '2026-01-05 10:00:00' a.txt   # mtime을 과거로 맞춤
sleep 2
cp a.txt b.txt        # 그냥 복사
cp -p a.txt c.txt     # 시각 등을 보존하며 복사
mv a.txt d.txt        # 이름만 바꾸기
for f in b.txt c.txt d.txt; do echo "== $f"; stat -c 'mtime=%y
ctime=%z
birth=%w' $f; done
```

실제 출력이다 (시각은 UTC).

```text
== b.txt
mtime=2026-11-24 04:13:49.774877350 +0000
ctime=2026-11-24 04:13:49.774877350 +0000
birth=2026-11-24 04:13:49.769608603 +0000
== c.txt
mtime=2026-01-05 10:00:00.000000000 +0000
ctime=2026-11-24 04:13:49.776519412 +0000
birth=2026-11-24 04:13:49.774877350 +0000
== d.txt
mtime=2026-01-05 10:00:00.000000000 +0000
ctime=2026-11-24 04:13:49.776519412 +0000
birth=2026-11-24 04:13:47.765608532 +0000
```

읽는 법은 이렇다.

- **`b.txt`(그냥 `cp`)**: mtime이 2026-01-05가 아니라 복사한 순간이다. 새 파일을 만들고 내용을 *쓴* 것이니 "방금 수정됨"으로 기록된다.
- **`c.txt`(`cp -p`)**: mtime이 원본과 같은 2026-01-05 10:00:00이다. [GNU coreutils 문서](https://www.gnu.org/software/coreutils/manual/html_node/cp-invocation.html)에 따르면 `-p`는 `--preserve=mode,ownership,timestamps`와 같고, `timestamps`는 "마지막 접근·수정 시각"을 보존한다.
  하지만 **birth(만든 시각)와 ctime은 복사한 순간**이다. 복사본이 새로 만들어진 사실까지 되돌릴 수는 없다.
- **`d.txt`(`mv`)**: 같은 파일이라 mtime도 birth(04:13:47, 맨 처음 만든 시각)도 그대로다.
  ctime만 이동한 순간으로 바뀌었다. 이 ext4에서 관찰한 결과이고, 위 man 페이지는 이름 변경이 ctime을 바꾼다고 명시하지 않는다.

## ctime은 과거로 돌릴 수 없다

mtime은 `touch -d`로 아무 날짜나 넣을 수 있다. ctime은 어떨까. `c.txt`의 mtime을 2020년으로 돌려 봤다.

```bash
touch -d '2020-01-01' c.txt
stat -c 'mtime=%y ctime=%z' c.txt
```

```text
mtime=2020-01-01 00:00:00.000000000 +0000 ctime=2026-11-24 04:13:49.781868365 +0000
```

mtime은 2020년으로 갔지만 ctime은 방금 시각으로 올라갔다. 시각을 *바꾸는 행위 자체*가 파일 정보의 변경이라 ctime이 갱신되기 때문이다. 그래서 "수정한 날짜"는 마음대로 바꿀 수 있어도, ctime을 보면 언제 건드렸는지 흔적이 남는다.

## 정리

- 수정한 날짜가 복사한 시각으로 바뀌는 건 오류가 아니다. 복사는 새 파일을 만들고 내용을 쓰는 일이라서다.
- 원본의 수정 시각을 유지하려면 `cp -p` (또는 `--preserve=timestamps`). 그래도 만든 시각은 복사한 순간이다.
- 이름을 바꾸거나 같은 파일시스템 안에서 옮기는 것(`mv`)은 새 파일이 아니므로 mtime과 birth를 유지한다.
- 시각 보존 여부는 도구마다 다르다. 압축 해제·동기화·파일 관리자 복사 같은 도구는 확인하지 않았다.

같은 "옮기기"인데 속도가 다른 이유는 [같은 드라이브 안에서 파일을 옮기면 순식간인 이유]({% post_url 2026-11-15-move-same-drive-instant-vs-copy %})에 있다. `mv`가 새 파일을 만들지 않는다는 점이 이 글의 `d.txt` 결과와 이어진다.
