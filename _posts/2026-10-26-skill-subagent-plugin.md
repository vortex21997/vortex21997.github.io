> **2026-10 기준.** [스킬](https://code.claude.com/docs/en/skills), [서브에이전트](https://code.claude.com/docs/en/sub-agents),
> [명령어](https://code.claude.com/docs/en/commands) 공식 문서를 근거로 정리했다.
{: .prompt-info }

Claude Code 문서를 읽다 보면 **스킬, 커스텀 명령어, 서브에이전트, 플러그인**이 계속 나온다.
비슷한 말처럼 들려서 뭘 언제 써야 할지 애매한데, 정리하면 축이 두 개다.

## 축 ①: 컨텍스트를 공유하는가

이게 **스킬과 서브에이전트를 가르는 유일한 기준**이다.

| | 컨텍스트 |
|---|---|
| **스킬** | 메인 대화에서 그대로 실행된다. 지금까지의 대화를 다 본다 |
| **서브에이전트** | **별도 컨텍스트 창**에서 돈다. 대화 기록을 못 본다. 결과 요약만 돌려준다 |

서브에이전트는 자기만의 시스템 프롬프트, 자기만의 도구 접근 권한, 독립된 권한 설정을 갖는다.
초기 컨텍스트에 들어가는 건 자기 시스템 프롬프트, Claude가 쓴 위임 메시지,
`CLAUDE.md`, git 상태 스냅샷 정도다.

### 그래서 언제 뭘 쓰나

**스킬** — 지금 하던 작업의 맥락이 필요할 때.
"이 블로그 규칙대로 글 써줘" 같은 건 지금까지의 대화를 알아야 한다.

**서브에이전트** — 출력이 시끄러운 작업. 테스트 로그, 검색 결과, 문서 수십 페이지.
**그 쓰레기가 서브에이전트 창에 남고 요약만 돌아온다.** 메인 컨텍스트가 안 더러워진다.

공식 문서도 이걸 비용 절감 방법으로 든다. 로그 1만 줄을 메인에서 읽는 대신
서브에이전트에 넘기면 토큰이 수만에서 수백으로 준다.

> 예외가 하나 있다. **fork**는 부모 대화를 그대로 물려받는 서브에이전트다.
> 격리가 목적이 아니라 "같은 맥락으로 다른 방향을 동시에 시도"가 목적일 때 쓴다.
{: .prompt-tip }

## 축 ②: 어떻게 배포되는가

**플러그인은 셋 중 하나가 아니다. 나머지를 담아 나르는 상자다.**

```
플러그인/
├── skills/      → 스킬들
├── agents/      → 서브에이전트들
├── commands/    → 명령어들
└── hooks/       → 훅 설정
```

플러그인을 켜면 그 안의 스킬·서브에이전트가 **이름 앞에 접두사가 붙어서** 들어온다.
`/plugin-name:skill-name`, `my-plugin:code-reviewer` 처럼.

즉 "플러그인 vs 스킬"은 비교 대상이 아니다. "직접 만들 거냐, 남이 만든 묶음을 받을 거냐"의 차이다.

## 커스텀 명령어는 어디 있나

예전에는 `.claude/commands/`에 `.md` 파일을 두면 `/이름`이 됐다.
**지금은 커스텀 명령어와 스킬이 같은 것**이다. 둘 다 `/이름`을 만들고 동일하게 동작한다.

```
.claude/commands/deploy.md          → /deploy   (예전 형식, 계속 동작)
.claude/skills/deploy/SKILL.md      → /deploy   (지원 파일과 추가 기능 사용 가능)
```

폴더 형식이 나은 점은 **참고 파일을 같이 담을 수 있다**는 것이다.
체크리스트, 템플릿, 스크립트를 스킬 폴더에 넣고 본문에서 참조하면 된다.

## 파일 위치 정리

| | 위치 | 범위 |
|---|---|---|
| **스킬** | `~/.claude/skills/<이름>/SKILL.md` | 내 모든 프로젝트 |
| | `.claude/skills/<이름>/SKILL.md` | 이 저장소 (커밋해 공유) |
| **서브에이전트** | `~/.claude/agents/<이름>.md` | 내 모든 프로젝트 |
| | `.claude/agents/<이름>.md` | 이 저장소 |
| **플러그인** | 설치하면 자기 디렉터리 | 플러그인을 켠 곳 |

이름이 겹치면 **프로젝트 것이 개인 것을 이긴다.** 우선순위는 높은 쪽부터
관리형 설정 → `--agents` 플래그 → 프로젝트 → 개인 → 플러그인 순이다.

## 서브에이전트 만들기

마크다운 파일 하나면 된다. 본문이 그대로 시스템 프롬프트가 된다.

```markdown
---
name: code-reviewer
description: 코드 품질과 관례를 검토한다. 코드를 고친 뒤에 쓴다.
tools: Read, Glob, Grep
model: sonnet
---

너는 코드 리뷰어다. 품질·보안·관례 관점에서 구체적이고
실행 가능한 피드백을 준다.
```

필수는 `name`과 `description` 둘뿐이다. 나머지는 선택이고, 중요한 것 몇 개만 보면:

| 필드 | 의미 |
|---|---|
| `description` | **Claude가 언제 이 에이전트를 부를지 판단하는 근거.** 여기에 공들여야 한다 |
| `tools` | 쓸 수 있는 도구 목록. 생략하면 상속 |
| `model` | 이 에이전트가 쓸 모델. 단순 작업이면 `haiku`로 두면 싸다 |
| `omitClaudeMd` | `true`면 `CLAUDE.md`를 안 읽는다 |
| `isolation` | `worktree`면 별도 git worktree에서 돈다 |

필드 이름은 **camelCase**이고, **인식 못 하는 필드는 조용히 무시된다.**
오타를 내도 에러가 안 나니 동작이 이상하면 철자부터 보는 게 좋다.

## 정리

| | 무엇 | 컨텍스트 | 언제 |
|---|---|---|---|
| **스킬** | 재사용할 지시·워크플로 | 메인 대화 공유 | 지금 맥락이 필요할 때 |
| **서브에이전트** | 전용 시스템 프롬프트를 가진 보조 | **분리** | 출력이 시끄러운 작업 |
| **커스텀 명령어** | 스킬과 같은 것 | 메인 대화 공유 | 반복해서 치는 지시 |
| **플러그인** | 위 셋을 담은 배포 단위 | 담긴 것에 따름 | 남의 묶음을 받거나 팀에 배포할 때 |

헷갈릴 때 던질 질문 하나로 줄이면 이거다.
