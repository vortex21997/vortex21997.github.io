> **2026-10 기준.** [공식 명령어 레퍼런스](https://code.claude.com/docs/en/commands)를 근거로 정리했다.
> 명령어는 버전마다 추가·제거되므로, 내 환경의 목록은 `/help`로 확인하는 편이 정확하다.
{: .prompt-info }

Claude Code에서 `/`를 치면 목록이 쏟아진다. 세어 보니 **119개**다.
전부 외울 필요는 없고, 그럴 수도 없다. **작업 흐름의 어느 시점에 쓰는지**로 묶으면 정리가 된다.

## 저장소에서 처음 쓸 때

| 명령어 | 하는 일 |
|---|---|
| `/init` | `CLAUDE.md` 초안을 만들어 준다 |
| `/memory` | 그 `CLAUDE.md`를 열어 다듬는다 |
| `/permissions` | 허용·질문·거부 규칙을 대화형으로 설정 |
| `/mcp` | 프로젝트에 필요한 MCP 서버 연결 |

이 네 개를 한 번 돌려두면 그 뒤 세션이 전부 편해진다.
특히 `/permissions`는 **매번 누르던 허락 버튼을 없애는** 작업이라 체감이 가장 크다.

## 작업 중

| 명령어 | 하는 일 |
|---|---|
| `/plan` | 플랜 모드로 전환. 큰 변경 전에 계획부터 세우게 한다 |
| `/model` | 모델 전환 |
| `/effort` | 추론 강도 조절 |
| `/context` | 지금 컨텍스트를 뭐가 채우고 있는지 색깔 격자로 보여준다 |
| `/compact` | 대화를 요약해 공간을 비운다 |
| `/btw` | **대화 기록에 안 남는 곁가지 질문** |
| `/diff` | 작업 트리 변경사항 확인 (Claude가 고친 것 포함) |

`/btw`가 의외로 유용하다. "지금 이 함수 뭐였지?" 같은 걸 물어볼 때
대화 기록을 오염시키지 않는다. 긴 세션에서 컨텍스트를 아끼는 방법이기도 하다.

`/context`는 **"왜 이렇게 느리지" 싶을 때** 먼저 보는 곳이다.
MCP 서버나 비대한 `CLAUDE.md`가 자리를 먹고 있는 게 바로 보인다.

## 내보내기 전

| 명령어 | 하는 일 |
|---|---|
| `/code-review` | 현재 diff를 검토. `--fix`로 바로 적용도 된다 |
| `/security-review` | 브랜치 변경분의 보안 취약점 검사 |

`/code-review`는 PR 번호를 넘길 수도 있다. `/code-review high 1234` 처럼
검토 강도와 대상을 같이 준다. `/review`는 같은 것의 별칭이다.

## 세션 사이

| 명령어 | 하는 일 |
|---|---|
| `/clear` | 컨텍스트를 비우고 새로 시작 (프로젝트 메모리는 유지) |
| `/rename` | 세션에 이름을 붙인다 |
| `/resume` | 이전 대화로 복귀 |
| `/branch` | 지금 대화를 분기해서 다른 방향 시도 |
| `/rewind` | 대화와 코드를 이전 체크포인트로 되돌린다 |

**`/rename` → `/clear` → 나중에 `/resume`** 이 조합을 쓰면,
컨텍스트는 비우면서 이전 작업을 잃지 않는다.
이름을 안 붙이고 `/clear` 하면 나중에 찾기 어렵다.

`/rewind`는 **코드까지 되돌린다.** Claude가 엉뚱한 방향으로 파일을 여러 개 고쳐놨을 때,
`git checkout`을 손으로 하는 것보다 빠르다.

## 뭔가 잘못됐을 때

| 명령어 | 하는 일 |
|---|---|
| `/doctor` | 설치·설정·`CLAUDE.md`·권한 문제를 진단하고 고쳐준다 |
| `/status` | 어떤 설정 파일이 로드됐는지, 모델·계정·연결 상태 |
| `/debug` | 디버그 로그를 켜고 런타임 문제를 추적 |
| `/usage` | 세션 비용, 플랜 사용량, 사용 내역 |

**설정이 안 먹을 때는 `/status`부터**다. 추측하지 말고 로드된 파일 목록을 보면 된다.
`/doctor`는 거기서 한 발 더 나가서 원인을 짚고 고치겠냐고 물어본다.

## 알아두면 좋은 것 몇 개

- **`/usage`** 는 플랜 사용량뿐 아니라 **뭐가 사용량을 먹는지 비율로** 보여준다.
  `25% Trim ~/code/api/CLAUDE.md · 49k tokens per request` 같은 식이다.
  footer에 `f to fix` 가 뜨면 눌러서 바로 적용할 수도 있다.
- **`/insights`** 는 최근 세션들을 분석해 HTML 리포트를 만든다.
  토큰이 아니라 **내가 어떻게 일하는지**를 보는 쪽이다.
- **명령어는 메시지 맨 앞에서만 인식된다.** 뒤에 붙인 텍스트는 인자가 된다.
- 여러 개를 한 메시지에 이어 붙일 수 있다. `/skill-a /skill-b 이것 좀 해줘` 처럼
  최대 6개까지 체인이 된다.
- Claude가 응답 중에 명령어를 보내면 큐에 들어가 턴이 끝난 뒤 실행된다.
  단 `/status`, `/tasks`, `/usage`는 **끼어들지 않고 바로** 실행된다.

## 내 명령어 만들기

반복해서 치는 지시가 있다면 명령어로 만들면 된다.
**커스텀 명령어와 스킬은 이제 같은 것**이라, 둘 중 아무 형식이나 `/이름`이 된다.

| 위치 | 적용 범위 |
|---|---|
| `~/.claude/skills/<이름>/SKILL.md` | 내 모든 프로젝트 |
| `.claude/skills/<이름>/SKILL.md` | 이 저장소 (커밋해서 공유) |
| `.claude/commands/<이름>.md` | 이 저장소 (예전 형식, 계속 동작) |

최소 형태는 이렇다.

```markdown
---
description: 블로그 글을 쓰고 배포까지 확인한다
argument-hint: [주제]
allowed-tools: Bash(bundle exec jekyll build) Bash(git push *)
---

$ARGUMENTS 주제로 글을 쓴다.
1. CLAUDE.md의 분류 체계에 맞춰 카테고리를 고른다
2. 빌드가 통과하는지 확인한다
3. 커밋하고 푸시한 뒤 Actions가 성공했는지 본다
```

- `description`은 **Claude가 이 명령어를 언제 불러올지 판단하는 근거**다. 핵심 용도를 앞에 쓴다.
- `allowed-tools`는 그 턴 동안 묻지 않고 쓸 도구다. 다른 도구를 막는 건 아니다.
- `$ARGUMENTS`는 인자 전체, `$0` `$1`은 위치별 인자다.
- 하위 폴더를 만들면 접두사가 붙는다. `.claude/commands/blog/write.md` → `/blog:write`

## 정리

119개 중에 매일 쓰는 건 이 정도다.

```
/init /memory /permissions     저장소 처음 세팅할 때 한 번
/plan /context /compact /btw   작업 중
/diff /code-review             내보내기 전
/rename /clear /resume         세션 사이
/status /doctor                안 될 때
```

나머지는 **필요해졌을 때 `/`를 쳐서 찾으면 된다.**
목록에서 이름으로 필터링되니, 외우는 것보다 "이런 게 있었다"만 기억하는 편이 낫다.
