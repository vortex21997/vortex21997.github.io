**인증 앱과 서버는 코드를 주고받지 않습니다.** 둘이 처음에 같은 비밀 키를 하나 나눠 갖고, 그 뒤로는 각자 "비밀 키 + 지금이 몇 번째 30초 구간인가"로 같은 계산을 합니다. 시계만 맞으면 같은 숫자가 나옵니다. 이 방식을 TOTP(Time-based One-Time Password, 시간 기반 일회용 비밀번호)라고 하며 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)에 정의되어 있습니다.

## 계산은 세 단계

1. 현재 유닉스 시각(1970-01-01부터 지난 초)을 30으로 나눠 **정수 몫 T**를 구합니다. 같은 30초 안에서는 T가 같습니다.
2. 비밀 키로 T를 HMAC-SHA1(키를 섞어 만드는 해시)에 넣어 20바이트를 얻습니다.
3. 그 20바이트에서 4바이트를 골라 숫자로 읽고, 10의 6제곱으로 나눈 나머지를 6자리로 맞춥니다. 고르는 방식은 [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226)의 "dynamic truncation"입니다.

```python
import hmac, hashlib, struct

def hotp(key, counter, digits=6):
    h = hmac.new(key, struct.pack(">Q", counter), hashlib.sha1).digest()
    o = h[-1] & 0xf                                   # 마지막 바이트의 아래 4비트가 시작 위치
    n = struct.unpack(">I", h[o:o+4])[0] & 0x7fffffff # 4바이트, 부호 비트 제거
    return str(n % 10**digits).zfill(digits)

def totp(key, t, step=30, digits=6):
    return hotp(key, t // step, digits)
```

## 공식 예제와 맞는지 확인

RFC 6238 부록 B는 키 `12345678901234567890`, 8자리 기준의 정답표를 줍니다. 위 코드로 돌린 결과입니다(Python 3.11.18).

```text
59 1 0x1 94287082
1111111109 37037036 0x23523ec 07081804
```

문서의 SHA1 행(`59 → 94287082`, `1111111109 → 07081804`)과 같습니다. 두 번째 값이 `0`으로 시작하는 것도 그대로 나오므로 자릿수를 `zfill`로 채워야 합니다.

## 30초 구간이 경계에서 바뀌는 모습

같은 키로 6자리를 뽑아 시각만 바꿔 보았습니다.

```text
t= 0  T= 0 755224
t= 29 T= 0 755224
t= 30 T= 1 287082
t= 59 T= 1 287082
t= 60 T= 2 359152
```

29초와 30초 사이에서만 숫자가 바뀝니다. 앱의 코드가 "시작한 시각부터 30초"가 아니라 **시계의 0초·30초 경계**에서 바뀌는 이유입니다.

## 그래서 생기는 일

- **휴대폰 시계가 틀리면 코드가 틀립니다.** T가 달라지기 때문입니다. 시간이 자동 설정이어야 합니다. (서버는 보통 앞뒤 한두 구간을 함께 허용하지만, 허용 폭은 서비스마다 다르므로 여기서 확인한 값이 아닙니다.)
- **QR 코드에는 비밀 키가 들어 있습니다.** 위 예제 키를 base32로 바꾸면 `GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ` 형태가 되는데, 앱에 등록할 때 보이는 문자열이 이것입니다. 이 키를 가진 사람은 코드를 계산할 수 있으니 화면 캡처를 남기지 않는 편이 안전합니다.
- **통신이 없어서 비행기 모드에서도 코드가 나옵니다.** 계산이 폰 안에서 끝나기 때문입니다.

> 확인 범위: RFC 6238의 SHA1 테스트 값을 직접 재현했습니다. 특정 서비스·앱이 허용하는 시간 오차나 SHA256/512 사용 여부는 확인하지 않았습니다.
