결론부터: `0.1`과 `0.2`는 2진수로 딱 떨어지지 않아 **이미 조금씩 어긋난 값**으로 저장된다. 둘을 더한 정확한 합은 표현 가능한 두 double의 **정확히 중간**에 떨어지고, 동점이면 가수의 마지막 비트가 짝수인 쪽으로 반올림하는 규칙 때문에 `0.3`이 아닌 이웃이 나온다.

환경: Python 3.11.17, Node v22.22.0, x86_64 리눅스 샌드박스. 둘 다 IEEE 754 binary64(double)를 쓴다. 형식 설명은 [Python 공식 튜토리얼의 부동소수점 장](https://docs.python.org/3/tutorial/floatingpoint.html)을 따랐다.

## 증상

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
```

Node에서도 `console.log(0.1+0.2)`는 `0.30000000000000004`다. 언어 문제가 아니라 형식 문제다.

## 저장된 비트 찍어 보기

`struct`로 double의 8바이트를 꺼내 부호(1) · 지수(11) · 가수(52)로 나눴다.

```python
import struct
b = struct.unpack('>Q', struct.pack('>d', 0.1))[0]
s = f'{b:064b}'
print(s[0], s[1:12], s[12:])
```

```
0.1      0 01111111011 1001100110011001100110011001100110011001100110011010
0.2      0 01111111100 1001100110011001100110011001100110011001100110011010
0.1+0.2  0 01111111101 0011001100110011001100110011001100110011001100110100
0.3      0 01111111101 0011001100110011001100110011001100110011001100110011
```

`0.1`과 `0.2`의 가수는 같고 지수만 1 다르다(2배). `1001`이 반복되는 무한 소수를 52비트에서 자르면서 끝이 `...1001 1001 1010`으로 **올림**됐다. 그래서 실제 저장값은 이렇다.

```
Decimal(0.1) = 0.1000000000000000055511151231257827021181583404541015625
Decimal(0.2) = 0.200000000000000011102230246251565404236316680908203125
Decimal(0.3) = 0.299999999999999988897769753748434595763683319091796875
```

`0.1`, `0.2`는 실제보다 크고 `0.3`은 실제보다 작게 저장된다.

## 덧셈은 어디서 갈리나

저장된 두 값의 합을 `Decimal`로 정확히 계산하고, `0.3`의 저장값(`lo`)과 `0.1 + 0.2`의 결과(`hi`)의 중점과 비교했다.

```python
from decimal import Decimal as D, getcontext
getcontext().prec = 60   # 기본 28자리면 합이 잘려서 비교가 틀어진다
s = D(0.1) + D(0.2)
lo, hi = D(0.3), D(0.1 + 0.2)
print(s)
print((lo + hi) / 2 == s)
```

```
0.3000000000000000166533453693773481063544750213623046875
True
```

정확한 합이 표현 가능한 이웃 두 개(`0x3fd3333333333333`, `0x3fd3333333333334`)의 **정확한 중점**이다. 동점이면 IEEE 754 기본 모드는 가수 마지막 비트가 0(짝수)인 쪽을 고른다. `...0011`은 홀수, `...0100`은 짝수라 후자가 선택됐다.

```python
>>> (0.1+0.2).hex(), (0.3).hex()
('0x1.3333333333334p-2', '0x1.3333333333333p-2')
```

두 값의 차이는 가수 정수로 1, 즉 이 크기에서의 최소 간격(`math.ulp(0.3)` = `5.551115123125783e-17`)이다. `0.1 + 0.2 - 0.3`이 정확히 이 값으로 찍힌다.

## 판별법: 오차가 아니라 "한 칸 차이"인가

- 차이가 `math.ulp` 한 칸 안팎이면 위와 같은 표현·반올림 문제다. 비교는 `math.isclose(0.1+0.2, 0.3)`(`True`)처럼 허용 오차로 한다.
- 차이가 여러 칸이면 연산을 많이 거치며 오차가 쌓인 것이다. 이 글의 설명으로는 부족하다.

> 이 결과는 위 환경에서 확인한 것이다. 반올림 규칙(동점 시 짝수)은 IEEE 754 기본 모드 기준이며, 이 글에서는 표준 원문이 아니라 위 Python 문서와 실행 결과로 확인했다.
