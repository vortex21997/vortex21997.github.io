결론부터: 여러 바이트로 된 숫자를 메모리에 놓을 때 **낮은 자리 바이트를 앞에 두는 방식(리틀 엔디언)**과 **높은 자리 바이트를 앞에 두는 방식(빅 엔디언)**이 둘 다 있고, 이 샌드박스의 CPU는 리틀 엔디언이다.
그래서 `0x12345678`을 메모리에서 한 바이트씩 읽으면 `78 56 34 12`가 나온다. 값이 바뀐 게 아니라 **바이트를 늘어놓는 순서**만 다르다. 반면 네트워크로 나가는 바이트는 `12 34 56 78` 순서로 약속돼 있어서 변환 함수가 필요하다.

> 환경: Linux 6.18, Intel Xeon @ 2.10GHz(`lscpu`의 Byte Order: Little Endian), gcc 13.3.0, Python 3.11.18. 아래 출력은 직접 실행한 것이다.
{: .prompt-info }

## C로 메모리의 바이트를 직접 읽기

4바이트 정수를 `unsigned char`(1바이트) 포인터로 한 칸씩 읽는다.

```c
#include <stdio.h>
#include <stdint.h>
#include <arpa/inet.h>
int main(){
 uint32_t x=0x12345678; unsigned char*p=(unsigned char*)&x;
 printf("host  : ");for(int i=0;i<4;i++)printf("%02x ",p[i]);puts("");
 uint32_t n=htonl(x); p=(unsigned char*)&n;
 printf("htonl : ");for(int i=0;i<4;i++)printf("%02x ",p[i]);puts("");
 return 0;}
```

```
host  : 78 56 34 12 
htonl : 12 34 56 78 
```

`host`가 이 컴퓨터가 메모리에 놓은 순서이고, `htonl`(host to network long)을 거치면 바이트가 뒤집혀 `12 34 56 78`이 된다.

## Python으로 같은 값을 두 방식으로 만들기

`struct`의 `<`는 리틀, `>`는 빅 엔디언이다([struct 문서의 Byte Order, Size, and Alignment](https://docs.python.org/3/library/struct.html)).

```python
import struct,sys
print(sys.byteorder)
print(struct.pack('<I',0x12345678).hex(' '))
print(struct.pack('>I',0x12345678).hex(' '))
print(struct.pack('=I',0x12345678).hex(' '))
```

```
little
78 56 34 12
12 34 56 78
78 56 34 12
```

`=`(이 컴퓨터의 기본 순서)가 `<`와 같은 결과다.

## 같은 바이트를 다르게 읽으면 다른 숫자가 된다

`12 34 56 78` 네 바이트를 어떤 순서로 읽느냐에 따라 값이 달라진다.

```python
b=bytes([0x12,0x34,0x56,0x78])
print(hex(int.from_bytes(b,'little')),hex(int.from_bytes(b,'big')))
```

```
0x78563412 0x12345678
```

파일을 열어 보면 이 차이가 그대로 보인다. `12 34 56 78`을 파일로 쓰고 `od`로 읽었다.

```
$ od -An -tx1 f.bin     # 바이트 단위
 12 34 56 78
$ od -An -tx4 f.bin     # 4바이트를 정수 하나로 읽기
 78563412
```

파일 안의 바이트는 그대로인데, 정수로 읽으면 이 컴퓨터는 `78563412`로 해석한다. 다른 컴퓨터에서 만든 바이너리 파일을 읽었더니 숫자가 엉뚱하게 나온다면 이 순서부터 의심할 만하다.

## 네트워크는 빅 엔디언으로 약속돼 있다

IP를 정의한 [RFC 791의 Appendix B](https://www.rfc-editor.org/rfc/rfc791.txt)는 이렇게 말한다. 여러 옥텟(8비트 묶음)으로 된 숫자는 "the most significant octet is transmitted first", 즉 **가장 높은 자리 바이트를 먼저** 보낸다. 이것이 흔히 말하는 네트워크 바이트 순서다.

리틀 엔디언 컴퓨터는 이 약속과 메모리 순서가 반대라서 `htonl`/`htons`로 뒤집는다.

```python
import socket
print(hex(socket.htons(0x1234)))
```

```
0x3412
```

`htons`는 2바이트 값을 뒤집는다. 포트 번호나 IP 헤더 필드를 만들 때 이 변환을 빼먹으면 `0x1234`가 `0x3412`로 나가 버린다.

## 정리

- 메모리 순서: 이 컴퓨터는 낮은 자리 바이트가 먼저(`78 56 34 12`). `lscpu`나 `sys.byteorder`로 확인한다.
- 값 자체는 같다. 바뀌는 건 바이트를 놓는 순서뿐이다.
- 파일·네트워크로 바이트를 주고받을 때는 양쪽이 순서를 합의해야 하고, 네트워크의 합의는 빅 엔디언이다.

확인하지 못한 것: 빅 엔디언 CPU에서 직접 돌려 보지는 못했다. 그쪽 동작은 위 설명과 RFC의 규정에 근거한 것이다.
