결론부터: 컴퓨터는 8비트 안에 들어가는 비트 패턴만 갖고 있고, 그중 **맨 앞 비트가 1이면 음수로 읽기로 약속**했기 때문이다.
`01111111`(127)에 1을 더하면 `10000000`이 되는데, 이 패턴을 약속대로 읽으면 -128이다. 계산이 틀린 게 아니라 읽는 방식 때문이다.

> 환경: Linux 6.18, Intel Xeon @ 2.10GHz, gcc(`-O0`), Python 3.11.18. 직접 실행한 출력이다.
{: .prompt-info }

## 같은 비트, 다른 숫자

2의 보수는 음수 -x를 "비트를 뒤집고 1을 더한 것"(= 2^N − x)으로 쓰는 방식이다.

```python
for n in (5,-5,127,-128):
    print(n, format(n & 0xFF,'08b'))
print(-5 & 0xFF, (~5+1)&0xFF)
```

```
5 00000101
-5 11111011
127 01111111
-128 10000000
251 251
```

`-5`의 비트는 `5`를 뒤집은 `11111010`에 1을 더한 `11111011`이고, 이 비트를 부호 없는 수로 읽으면 251이다.
저장된 건 비트뿐이고, 부호 있는 수로 읽느냐 없는 수로 읽느냐가 다르다.

## 127 + 1 실행

```c
int8_t a=127; a=(int8_t)(a+1);
printf("int8 127+1 = %d\n", a);
uint32_t u=(uint32_t)-1; printf("-1 as uint32 = %u (0x%08X)\n",u,u);
uint32_t w=(uint32_t)INT32_MAX+1u; printf("%d\n",(int32_t)w);
uint8_t b=200; printf("(int8_t)200 = %d\n",(int8_t)b);
```

```
int8 127+1 = -128
-1 as uint32 = 4294967295 (0xFFFFFFFF)
INT32_MAX+1 (unsigned wrap, read as int32) = -2147483648
(int8_t)200 = -56
```

- 32비트도 똑같다. `-1`은 `0xFFFFFFFF`이고, 최댓값 2147483647에 1을 더하면 `0x80000000`, 즉 -2147483648이다.
- 200은 `11001000`이다. 8비트 부호 있는 수로 읽으면 200 − 256 = -56이다.

GCC 문서는 큰 값을 더 좁은 부호 있는 정수형으로 바꿀 때 "the value is reduced modulo 2^N to be within range of the type; no signal is raised"라고 구현을 밝힌다([GCC: Integers implementation](https://gcc.gnu.org/onlinedocs/gcc/Integers-implementation.html), 2026-11 확인). 256으로 나눈 나머지를 취하는 것이 위의 결과와 같다.

> 위 변환 규칙은 `int8_t`로 *변환*할 때의 구현 정의 동작이다. 부호 있는 정수끼리의 덧셈 자체가 넘칠 때의 동작은 이 글에서 실행해 보지 않았다. 코드에서 오버플로를 기대하려면 부호 없는 정수로 계산하는 쪽이 안전하다.
{: .prompt-warning }

## Python은 왜 안 넘치나

```python
print(2**31-1, -2**31, 2**100+1)
```

```
2147483647 -2147483648 1267650600228229401496703205377
```

Python의 `int`는 비트 수가 고정되지 않아 넘치지 않는다. 8비트 동작을 보려면 `n & 0xFF`처럼 직접 자른다.
`struct.unpack('<b', bytes([200]))[0]`은 -56, `struct.unpack('<i', b'\xff\xff\xff\xff')[0]`은 -1, `'<I'`로 읽으면 4294967295가 나온다. 같은 바이트를 어떻게 읽느냐의 차이다.
